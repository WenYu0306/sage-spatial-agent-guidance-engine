# 难点解析 ① · LangGraph 编排：让一次对话变成可靠的多步工具流

> SAGE 的 Agent 层（agent-orchestrator）要解决的不是"会调工具"，
> 而是**每次调用都走同一条可预测的路径，错了有降级，每一步可回放**。
> 这篇讲四个设计：数据驱动计划步、跨步骤惰性求值、幻觉名单法校验、全链路 trace。

## 计划步：意图 → 计划是数据，不是代码

用户问句先过意图节点（JSON Schema 约束 + 重试），解析成
`poi_search / facility / navigate / promotion / venue_info / fallback` 之一。
每种意图对应一份**计划**：`_PLANNED_STEPS[plan_name](view, config)` 返回步骤列表——

- 每步是 `(tool_code, args)` 或 **`callable(results)`**；
- 执行循环只认预算：**6 次工具调用 / 12 秒**硬上限（PRD 口径），超限置 `degraded`；
- 同名工具去重（`seen` 集合），LLM 幻想出的"再查一次"不会放大成本。

为什么不让 LLM 自由决定"下一步调什么"？——测评口径要稳定：同一个问句，
今天走 search→rank，明天走 search→rank→route，评测基线就没法维护。
计划是配置，行为是可复现的；LLM 只负责它擅长的（理解）与表达（生成）。

## 跨步骤数据依赖：一个被评测掩盖两周的缺陷

M7 推荐接入后出现一个隐藏问题：`rank` 步骤恒拿空候选。根因在 LangGraph 的状态语义——

- 计划步骤在**节点入口一次性算好**，`view` 是当时的状态快照；
- 执行循环里同轮 `search` 的结果写入 `results`，但步骤列表里的 `args` 早在循环开始前就冻结了；
- 单工具意图（只有 search）看不出来，评测判据也没覆盖"rank 收到了什么"。

修复（已进回归测试 `test_rank_step_receives_same_turn_search_candidates`）：步骤支持
**`callable(results)`**——执行到该步时才解析参数，从累积结果里取同轮候选。这是
"计划静态、数据动态"的关键一格：计划描述调用拓扑，参数在执行期绑定。

## 幻觉名单法：安全网放在生成之后

LLM 编造店名是导视场景最高频、最致命的幻觉——用户会真的走过去。SAGE 的对策（ASSUMPTIONS A7）：

1. **名单法后置校验**：回答里出现的店名必须能在本轮工具结果（POI 列表、券关联门店名、知识检索命中）里找到；
2. **回声词过滤**：「附近咖啡店」这类话术回声不算编造（评测 E17 教的：安全网不能拦截正确回答）；
3. **校验不过 → 整条回答降级为列表卡片**——宁可不答，不可答错；
4. 拦截真实发生时记 `logger.warning` + trace 标记 `degraded`，可观测可统计。

边界同样诚实登记：数字/价格/时间类编造不在名单法覆盖内，转生产可叠加 NLI 类校验。

## trace 时间线：每一步都可回放

每次对话的所有步骤落 `agent_traces`：intent_parse → tool_call×N → generate，
每步带输入/输出（包裹截断，保证 JSON 永远合法——盲截 `[:2000]` 曾产出非法 JSON 让整轮 3001）、
状态、**真实时延与 token 用量**。前端 `/trace.html` 时间线可视化。

这直接喂给运维面 `/api/v1/agent/stats` 五指标：AI 调用成功率、降级率、错误码分布、
分步平均时延、trace 完整率——降级不是玄学，是曲线。

## 这层修过的坑（摘自 BUGFIX_LOG，全部带回归测试）

| 现象 | 根因 |
| :-- | :-- |
| 同会话累计 6 次工具调用后整轮锁死 | checkpointer 跨轮还原 tool_calls 不清零 |
| 多轮指代答非所问 | 无历史注入（session_id 线程 + 最近 6 条） |
| trace 截断致整轮 3001 | json.dumps[:2000] 盲截断 |
| F1 问厕被指去 B1 | 同名设施按并列 hot_score 随机选层 |

**一句话**：Agent 工程的难度不在"让它动"，在"让它每次都一样地动，坏了知道为什么"。
